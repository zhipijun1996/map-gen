# 《失序之钟》随机 Map 系统：生成算法与 Module 库建设指南

> **文档代号：** `MAP_GENERATION_GUIDE`  
> **版本：** 1.0  
> **状态：** 指导性文件（Recommended）  
> **适用范围：** 面向 Godot 在线肉鸽地图生成、Module 库建设、设计质量评估与逐阶段研发。  
> **最高优先级依据：** [`MAP_FOUNDATION.md`](MAP_FOUNDATION.md)。本文件所有推荐均在基础契约内实施；当两者不一致时，始终遵循基础文档。  
> **性质：** 给出可以直接落地的默认方案、初始参数和可比较的算法选择；数值可通过实验、试玩与区域差异迭代。

## 1. 整体方案与职责

系统的基本生产路线为：

`离线创作 Module → 认证 Port / Route / 封口 / 镜像 → 编译模块索引 → 在线生成探索骨架 → 在线矩形 Module 约束拼接 → 在线静态有向图验证与评分 → Godot 实例化地图`。

推荐采用**探索骨架驱动的约束生长（Goal-directed Constrained Growth）**：

- 先用纯程序生成玩家将体验到的主路线、分叉、汇合、奖励与环路等**结构意图**。
- 再联合选择矩形 Module、实际位置、镜像方向、连接 Port 和未连接 Port 的封口方案。
- 对开放通道采用前沿生长；对指定两端 Port 的闭环采用目标导向搜索。
- 使用约束传播、搜索启发式和有限回溯保证在线成本有界。
- 实际地图以所有真正可行的内部 Route 与已连接 Port 构图，随后进行可达性验证和体验排序。

**离线使用大模型，在线完全使用纯程序**，是贯穿所有推荐方案的职责边界。

## 2. 推荐的区域规模与玩法预算

以下为单个连续探索区域的初始设计目标：

| 项目 | 推荐起点 | 调整依据 |
|---|---:|---|
| Map 实例数 | **40～65 个 Module** | 实际探索时长与挑战密度 |
| 通向 Boss 的主要体验路线 | **2～3 套** | 路线动作和风险差异 |
| 奖励支路 | **5～8 条** | 奖励类别、路径成本、玩家探索反馈 |
| 主路共享与汇合 | 允许 | 体验差异是否明确 |
| 空间发展方向 | 四向皆可 | 区域特色和玩法主题 |
| 奖励支路类型 | 折返、单向环回、异位汇入 | 玩法节奏与奖励价值 |

这里的主路线数量是**可辨识的通关方案**数量，而不是图论意义上从 Start 到 Boss 的全部简单路径数量。交错、分叉和局部环路允许产生更多数学上的实际路径。

为每条主要体验路线制定一份轻量画像：

`route_profile = (mechanic_mix, difficulty_curve, estimated_time, combat_share, risk_reward_style)`

例如荆棘森林可以围绕钩索设置“高速危险捷径”和“较长但更安全的探索路线”；风铃平原则偏重反冲射击、基础跳跃和循序渐进的动作组合。路线区别优先体现于**动作方式与玩家抉择**，不只是长度或奖励数。

### 2.1 奖励支路配置

| 类型 | 拓扑 | 玩法目的 |
|---|---|---|
| 折返型 | 主路 → 挑战 → 奖励 → 原路返回 | 测试逆向穿越、明确的风险收益选择 |
| 单向环回型 | 主路 → 挑战 → 奖励 → 单向落差/初始通行的捷径 → 既有路线 | 制造探索循环并减少机械折返 |
| 异位汇入型 | 主路 A → 挑战 → 奖励 → 主路 B 或后续枢纽 | 形成路线切换与探索网络交错 |

奖励价值可结合额外操作难度、失败风险、时间成本、能力要求和可见性来配置。**空间深度只是其中一个维度**。机关开启后出现的新捷径可增强探索体验，但通用静态求解只使用初始有向关系；依赖动态机关才能脱困的完整机制应做成经离线认证的特殊结构。

## 3. Module 库：数量、尺寸与构成

### 3.1 推荐库规模

下表的数量指**离线制作并认证的基础 Module 模板数**；镜像仅增加在线方向候选，不增加原创内容模板数。

| 阶段 | 单区域基础 Module 库 | 主要用途 |
|---|---:|---|
| 建模与搜索原型 | **40～60** | 验证 Port、Route、封口、镜像、二维布局和闭环 |
| 可玩 Demo | **100～160** | 支持 40～65 个实例的多 Seed 地图与基础差异化 |
| 内容成熟 | **180～260** | 降低重复体验，提高常用连接的候选覆盖 |

以成熟阶段 **200 个基础 Module** 作为规划样本：

| 主职责标签 | 建议数量 | 比例 | 内容重点 |
|---|---:|---:|---|
| 穿越类 | 110 | 55% | 反冲位移、跳跃、钩索与连续动作链 |
| 分叉枢纽 | 30 | 15% | 多 Port、多 Route、路线切换与汇合 |
| 奖励类 | 30 | 15% | 额外挑战、宝箱、收集与回程结构 |
| 开阔空间 | 20 | 10% | NPC、地标、战斗与区域特色展示 |
| 特殊玩法 | 10 | 5% | Boss 入口、特殊机关与独特机制 |
| **合计** | **200** | **100%** |  |

此表仅是库建设的主职责配额。**一个 Module 可以兼具多种实际用途**；例如三 Port 穿越类模板在某个 Seed 中可以充当枢纽，在另一个 Seed 中可以只承担直线通行。分类型统计只为内容管理服务，不限制搜索匹配。

库的优先级应由**有效连接覆盖**决定，不是单纯扩大模板总数。建议按 `(入口 Port 类型及方向, 出口 Port 类型及方向, 能力集合, 动作主题, 难度段, 近似几何尺寸)` 统计可用的基础模板与镜像候选数量，并优先补足供给稀缺的高频组合。

### 3.2 推荐 Module 尺寸

以下全部直接以 **Block** 为单位，不引入额外槽位。假定默认 `Block = 128×128 px`：

| 用途 | 推荐尺寸（Block） | 对应典型像素尺寸 | 建设思路 |
|---|---|---|---|
| 短连接、节奏过渡 | `2×2`、`3×2`、`2×3` | 256×256、384×256、256×384 | 低复杂度转向与接口衔接 |
| 标准穿越主力 | **`4×3`、`3×4`** | 512×384、384×512 | 单段完整动作挑战，优先建设 |
| 横向动作链 | `5×3`、`6×3` | 640×384、768×384 | 横向反冲、钩索、连续平台 |
| 纵向动作链 | `3×5`、`3×6` | 384×640、384×768 | 攀爬、控制下落、纵向分支 |
| 枢纽与中型空间 | `4×4`、`5×4`、`6×4` | 512×512、640×512、768×512 | 多方向 Port 与明显的路线选择 |
| 大型开阔空间 | `6×5`、`6×6` | 768×640、768×768 | NPC、展示、复杂战斗或互动 |
| Boss / 专用空间 | `8×6`、`10×6` 等 | 1024×768、1280×768 | 按战斗可读性与镜头测试定制 |

建议的库尺寸分布：短小约 **20%**，标准 `4×3 / 3×4` 约 **30%**，长条形约 **25%**，中大型枢纽约 **15%**，大型专用约 **10%**。分布是模板制作预算，不必等于在线抽样权重。

尺寸可以根据角色跳跃高度、反冲速度、钩索射程、镜头和敌人活动范围调整；不要求所有尺寸互为倍数，也不限制 Module 必须摆在某种大网格的起点上。

### 3.3 推荐 Port 数量与功能复用

| 主职责 | 建议 Port 数量 | 优先设计内容 |
|---|---:|---|
| 普通穿越 | 2～3 | 一条鲜明主 Route，可有一个替代出口 |
| 多用途穿越 | 3～4 | 水平与纵向路线可独立组合 |
| 分叉枢纽 | 3～5 | 两条以上有意义的可选 Route |
| 开阔空间 | 4～6 | 多侧出入、地标与战斗体验 |
| 专用复杂结构 | 按需 | 机关、Boss 出入口、特殊玩法 |

Port 数量是负担与复用率之间的权衡。优先制作**多个有用、已验证的 Route**，而不是单纯增加无用途 Port。

## 4. 部分 Port 使用：Module 的多用途装配

一个 Module 可以拥有多个 Port 和多条 Module Route。**每次 Map 放置只需要连接与本次探索结构相关的部分 Port**；其余 Port 做局部封口处理。

### 4.1 三 Port 示例

设某模板含 `L`（左侧岩体 Input）、`R`（右侧岩体 Output）、`U`（顶部可穿平台 Inout）三个 Port，具有这些经过认证的有向 Route：

- `L→R`：普通水平穿越。
- `L→U`：钩索攀升。
- `U→R`：高处进入后向右离开。

则它可以有多种不同的 Map 用法：

| 本次已连接 Port | 典型作用 | 未连接 Port |
|---|---|---|
| `L, R` | 普通水平穿越 | `U` 封口 |
| `L, U` | 向上挑战 | `R` 封口 |
| `U, R` | 高处下行并接入主路 | `L` 封口 |
| `L, R, U` | 分叉与汇合枢纽 | 无 |

这个例子中的三条 Route 不会因“本次只计划其中一条”而在逻辑上自动消失。**若 L、R、U 全部连接，玩家可实际执行的其他 Route 同样存在**，Map Validator 必须将其纳入真实有向图，用于发现额外捷径、支路或绕行。

### 4.2 未使用 Port：推荐的轻量封口方式

优先使用 Module 内侧的一小段标准化封口 Cell，风格与区域一致：

- **荆棘平台 / 荆棘墙：** 适合风铃平原边缘、荆棘森林和危险空中出口；可组合实体碰撞阻挡，形成明确边界。
- **岩体块：** 适合地面、墙体和天然洞穴边缘。
- **短平台 + 危险障碍：** 适合保持画面自然，同时阻止玩家从未连接接口离开。

推荐离线为 Port 周边预留小面积 `closure_zone`，供标准封口块使用；在线只执行：

`Port 未连接 → 读取该 Port 预认证封口类型 → 放置封口 Cell`。

封口规则：

1. 局部封口完全位于本 Module 的矩形占用内。
2. 封口应真正阻断无效出口或可靠地终止越界；**只有扣血、但仍能穿出边界的荆棘不能算封口**。
3. 不改变本次必需 Route 的可达性。
4. 同时封闭多个 Port 时，封口之间与所保留路线的兼容性也得到离线验证。
5. 封口不需要作为新的 Module，也不需要增加在线玩家状态搜索。

一般情况下应让封口方案**局部且互不干扰**，这样在线不必枚举 `2^N` 个完整 Module 组合。若某个模板的不同封口组合会影响内部 Route，则离线明确记录可支持的连接/封口配置，并将其作为可检索的合法模式。

### 4.3 搜索时怎样避免组合爆炸

不要在线预先枚举每个 Module 的全部 Port 子集。

例如某连接任务需要“左侧岩体入口 → 上侧空中出口、使用钩索、难度 4”，候选查询直接按**必需 Route 签名**筛选。其他 Port 暂时保持可选：

`required_route + port_geometry + allowed_abilities + footprint + mirror → candidate list`

在完成 Map 规划后，统一确定每个实例的最终连接集合与封口集合。对可能影响路线的封口约束可在搜索阶段提前检查，避免末尾才发现不兼容。

把一个 Module 的基础模板、方向变体和用途签名分别管理：

- **基础模板数**：内容制作成本。
- **方向变体数**：运行时可选几何方向。
- **用途签名数**：不同连接任务能被满足的种类。

例如 200 个基础模板中，160 个允许镜像，40 个不允许；忽略完全对称的合并时最多产生 `160×2 + 40 = 360` 个方向候选。这**不等于 360 个独立 Module**，也不能简单乘以所有可用 Route 数当作“原创内容数量”。

## 5. 水平镜像的推荐实践

推荐每个可镜像 Module 在编译库时预生成原向与镜像方向的轻量索引：

- `module_017/normal`
- `module_017/mirrored`

两者共用基础内容 ID。镜像后的 Port 世界坐标、朝向、路线位移、相关方向动作及碰撞等均由基础契约确定；镜像可用性由离线测试确认。

**镜像按空间左右翻转，不是把 `L→R` 无条件改写成 `R→L` 的反向动作。** 入口与出口的逻辑身份保持：原来从左 Port 进入、右 Port 离开，镜像后仍是同一条经镜像的动作，只是入口落在右侧、出口落在左侧。

如果敌人动作、机关运动、文字、视觉构图或物理行为不适合镜像，为该模板设置 `allow_mirror_x = false`。镜像后的内容应以可复现的验证数据为依据。

## 6. 探索结构规划：纯程序图变换

推荐把**探索结构**实现为一组程序函数，而不是要求每张地图先生成 40～65 个抽象节点。

从 `Start → Boss` 的初始骨架出发，逐步应用图变换，形成若干已标注的结构任务：

| 操作 | 含义 | 约束重点 |
|---|---|---|
| `expand_path` | 一段抽象通道拆分为若干动作段 | 时长、动作组合、难度预算 |
| `split_path` | 在一个路段引出两条或多条方案 | 风险、难度、动作差异 |
| `add_rejoin` | 不同路线再次汇合 | 目标端口的物理可实现性 |
| `add_reward_branch` | 添加奖励支路 | 折返、单向环回、异位汇入三种去向 |
| `add_cross_connection` | 连通两条既有路线 | 新增路线选择而不是无意义连边 |
| `add_shortcut` | 插入初始可通行捷径 | 静态方向、奖励和路线长度 |

例如：

```text
                 反冲挑战 A —— 枢纽 H
               /                         \
Start —— 分叉                            汇合 —— Boss
               \                         /
                 钩索挑战 B —— 枢纽 J
                          \        /
                           奖励回路
```

图中的“挑战 A”不是指定尺寸的 Module，而是待实现的通行需求，可能由一个或多个 Module 实现。这样的规划可以优先控制路线意图，同时保留实际空间拼接的自由度。

推荐将任务划分为：

- **关键节点任务**：起点、Boss、主要枢纽、独特地标和特殊结构。
- **开放路线任务**：从某个 Port 向外继续生长，终点范围宽松。
- **指定连接任务**：从 A 的 Output 连到 B 的 Input，需要搜索一串 Module 完成接缝与闭环。
- **奖励支路任务**：附带奖励、挑战、回程形式及难度预算。

规划阶段可以同时记录“必须连接的结构”和“期望体验指标”。关键结构由后续求解结果反馈调整，而不把所有位置和 Module 类型提前锁死。

## 7. 在线空间求解：矩形放置 + Port 路径搜索

### 7.1 生成器输入输出

```text
GenerateMap(
    seed,
    biome,
    available_abilities,
    map_config,
    module_library_version
) -> GeneratedMap
```

输出包含：实例模板与位置、是否镜像、实际 Port 配对、未连接 Port 封口、实际有向通行图、奖励放置、生成种子及诊断信息。

同一组固定输入应得到确定性输出，便于复现和测试。

### 7.2 推荐七步流程

1. **预过滤和索引**：加载离线认证的区域 Module，筛掉能力不足的 Route，展开允许的镜像方向，构建 Port / Route / 尺寸索引。
2. **生成探索骨架**：确定起点、Boss、2～3 套主路线意图及奖励支路拓扑，对主要动作、难度和空间发展方向赋予目标。
3. **布置关键 Module**：先放置起点、Boss、主要枢纽及高约束特殊结构；位置保留可调整余地。
4. **优先完成高约束任务**：指定端点的环路、奖励汇入、难以匹配的 Port 连接先求解。
5. **补充普通路线**：从可用 Output Port 进行目标驱动的 Module 生长，补足挑战段与必要过渡段。
6. **完成所有连接和封口**：验证并确定每个实例实际启用的 Port，未连接 Port 用认证方案封闭；对封口影响 Route 的情形更新真实通行关系。
7. **验证与筛选**：构造实际有向图，检查硬约束、路线和奖励，再对可行候选评分，输出成功地图。

探索骨架与空间求解之间允许**有限反馈**：连接困难时先换候选、镜像、调整位置、插入过渡段，必要时局部调整图结构。

### 7.3 Module 几何放置

对已放置 A 的某个开放 Port，与候选 B 的兼容 Port 相连时，B 的 Block 原点可由两端局部 Port 坐标直接推出：

`origin_B = world_port_A − local_port_B`（使用一致的双倍 Block 坐标，必要时再除以 2）。

随后执行：

- 新矩形与已有实例是否重叠。
- Port 是否位于同一边界中心、朝向是否相反。
- 地貌类型是否相同，初始通行权限是否满足需求。
- 候选内部的指定 Route 是否经过认证且能力允许。
- 其他 Port 是否仍可用、可安全封口，或能够用于后续任务。

几何自由度集中于**选哪个 Module、哪个 Port、是否镜像**；不必逐像素搜索新位置。

### 7.4 路线填充与环路闭合

建议将两种搜索机制结合：

| 任务 | 机制 | 目标 |
|---|---|---|
| 开放式主路延伸 | 约束前沿生长 | 从有效 Output 接出一系列新 Module，发展地图空间 |
| 两个固定 Port 之间闭合 | 目标导向路径搜索 | 找到一串矩形不重叠、Port 精确匹配的 Module |
| 分叉枢纽匹配 | 多 Route 候选约束传播 | 用较少模板同时满足多条必要通路 |
| 奖励支路 | 组合任务 | 将动作挑战、奖励位置与返回方式一起实现 |

环路通常比普通前沿生长更受限，应尽早完成并为其预留可行空间。候选 Module 越大、目标 Port 越固定，越需要有效剪枝和回溯。

### 7.5 求解器实现建议

初版采用：

- **搜索策略**：随机化 Beam Search，或带启发式的 DFS + 有限回溯。
- **变量选择**：优先处理剩余候选少、必须闭环、端口特殊的任务（MRV 思路）。
- **空间检查**：Block 占用网格 / 位集与矩形重叠判断。
- **候选索引**：`(surface, face, permission, required_abilities, route_pattern, size, orientation)`。
- **评分启发式**：端口间目标距离、空间剩余量、未完成连接、Route 标签匹配、难度与重复惩罚。
- **执行预算**：每次生成设置节点展开上限、回溯上限和实际时间预算，并准备经过验证的备用地图。

不建议把每个 Cell 的实际物理运动、装备和动态机关状态引入在线 CSP；也不要求第一版就引入大型 CP-SAT 或复杂学习式生成器。后续可以在稳定基线上比较其他求解器。

## 8. 离线 Module 内容工厂与自增长库

离线工作流建议：

1. **需求分析**：统计区域主题和生成器对 Port 组合、尺寸、难度、动作主题的缺口。
2. **创作模块**：LLM/Codex 辅助制作矩形地形、Cell、敌人、机关、可选 Port 与 Route。
3. **明确接口**：记录每条 Route 的方向、能力要求、动作标签、难度、预计时长和资源特征。
4. **动作认证**：在 Godot 实机物理条件下验证各条声称可行的 Route，保留可追溯的成功轨迹或自动测试。
5. **复用认证**：验证允许镜像方向、常见 Port 子集、封口方案和相邻接缝；按需要记录哪些组合可同时使用。
6. **编译发布**：输出模块 ID、矩形尺寸、Port 坐标、实际 Route、封口配置、场景资源引用与多维索引。
7. **反馈增长**：收集在线求解失败的具体约束需求，离线补齐常用的欠缺连接，而非在正式在线生成时要求大模型临时补缺。

### 8.1 建议的离线 Module 请求

```yaml
module_request:
  biome: thorn_forest
  primary_role: traversal
  preferred_size_blocks: [4, 3]
  input_port:
    surface: ROCK
    face: LEFT
  output_port:
    surface: ONE_WAY_PLATFORM
    face: TOP
  required_abilities: [grapple]
  mechanic: narrow_space_grapple
  difficulty_target: 4
  extra_ports: optional
  allow_mirror_x: true
  unused_port_seal: thorn_barrier
  physical_validation: required
```

这是一种协作接口示意；实际项目可采用 Godot `Resource`、JSON、YAML 或其他可版本化格式。即使通过 LLM 设计，所声明的 Route 和封口仍需真实验证。

## 9. 数据结构与编译索引示例

下面是说明模块多用途、镜像与封口配置的**示例性数据片段**，不是强制的存储格式：

```json
{
  "id": "forest_grapple_017",
  "size_blocks": [4, 3],
  "allow_mirror_x": true,
  "ports": [
    {"id": "L", "edge_block": [0, 1], "face": "LEFT", "surface": "ROCK", "permission": "INPUT", "seal": "thorn_barrier"},
    {"id": "R", "edge_block": [3, 1], "face": "RIGHT", "surface": "ROCK", "permission": "OUTPUT", "seal": "thorn_barrier"},
    {"id": "U", "edge_block": [2, 0], "face": "TOP", "surface": "ONE_WAY_PLATFORM", "permission": "OUTPUT", "seal": "thorn_barrier"}
  ],
  "routes": [
    {"from": "L", "to": "R", "required_abilities": [], "difficulty": 2, "action_tags": ["recoil"], "validated": true},
    {"from": "L", "to": "U", "required_abilities": ["grapple"], "difficulty": 4, "action_tags": ["grapple"], "validated": true}
  ]
}
```

**说明：** 上面 U 采用顶部可穿平台 Output，可与相邻模块底边的同类型 Input 合法拼接；`thorn_barrier` 仅表示已认证的封口资源引用，不代表任意视觉荆棘都能直接充当封口。实际编译结果还需包含入口/出口动作条件、初始机关约束、资源与时间标签、封口组合认证、场景资源和测试记录。

建议编译期建立：

1. **基础 Module 索引**：区域、尺寸、动作、难度、主要职责。
2. **方向候选索引**：基础 ID + 原向/镜像；已去除不允许或等价的方向。
3. **Route 索引**：从/到 Port 类型、朝向、初始方向、必要能力位集。
4. **Port 兼容索引**：相邻接口的可配对候选。
5. **封口合法性索引**：本模板支持的未连接 Port 处理方案与受影响 Route 关系。

## 10. 在线 Map 验证与体验排序

### 10.1 每张地图的硬验收

生成器执行基础文档定义的全部强制条件。建议将验证器拆为以下独立过程：

| 验证模块 | 检查内容 |
|---|---|
| `validate_rectangles` | W×H 占用、整数坐标、实例间无重叠 |
| `validate_ports` | 坐标精确对齐、朝向相反、同类地貌及初始方向权限 |
| `validate_closures` | 所有未连接 Port 已合法封口，无非法越界 |
| `validate_routes` | 真实启用 Route 的离线认证、能力与封口兼容性 |
| `build_actual_graph` | 全部实际有效 Route 和跨实例连接均计入，包含非规划捷径 |
| `validate_reachability` | Start → Boss、配置中的必达奖励与回程关系 |
| `validate_budget` | Module 数量、主路线目标、奖励类别与数量等区域配置 |

静态验证回答的是“在初始方向和给定能力条件下，是否存在符合契约的通路”。Godot 物理动作验收与玩家试玩则衡量操作可靠性和真正的趣味。

### 10.2 体验评分的建议初始权重

| 指标 | 建议权重 | 具体评价 |
|---|---:|---|
| 主路线体验差异 | **25%** | 动作主题、难度、时长、风险取舍是否明显 |
| 动作挑战节奏 | **25%** | 连续动作链与节奏缓冲的分布 |
| 探索网络质量 | **20%** | 分叉、交错、汇合、环路和有意义的捷径 |
| 风险奖励匹配 | **15%** | 奖励收益和额外挑战、时间、风险的关系 |
| 内容重复控制 | **10%** | Module、Route 和连续动作序列重复度 |
| 空间利用 | **5%** | 上下左右发展与无效绕行程度 |
| **合计** | **100%** |  |

硬约束决定是否接受地图，软评分用于合格地图之间择优。所有指标应与试玩评价校准，避免单纯优化一个数值分数而牺牲手感或探索兴趣。

### 10.3 批量 Seed 评估

每个开发阶段建议分别统计：

- 有效 Map 比例、首次成功率、备用地图触发次数。
- 平均与高分位生成耗时、搜索展开节点、回溯次数。
- 指定目标 Port 闭环成功率、端口签名候选覆盖、封口导致的候选拒绝数。
- 主路线差异、奖励支路完成率、有效 Module 复用率、玩法重复率。
- 人工试玩的探索欲、动作爽快感、迷路感、难度节奏和奖励公平性。

指标以实际目标 PC/移动设备结果为准；生成时间上限和回退方案由产品性能预算定义。

## 11. 分阶段建设与验收

| 阶段 | 测试规模 | 交付成果 |
|---|---|---|
| P1：基础契约与实例拼接 | 10～20 个测试 Module | Block 矩形、Port 对齐、有向 Route、镜像、部分 Port 使用和荆棘封口全部可测试 |
| P2：探索骨架 | 40～60 个模板 | 图变换生成双路线、奖励折返、单向环回与重新汇合 |
| P3：二维约束求解 | 20～35 个地图实例 | 目标 Port 闭环、无重叠放置、局部回溯、完整实际有向图验证 |
| P4：可玩区域 Demo | 100～160 个模板；40～65 个地图实例 | 2～3 套主要路线、5～8 奖励支路及多 Seed 质量筛选 |
| P5：成熟内容生产 | 180～260 个模板 | 有效连接覆盖度、动作主题多样性、稳定生成与玩家盲测 |

### 11.1 建议的最小自动化测试集合

- 同一 Seed 和相同输入得到相同 Map。
- 两个不同矩形 Module 不允许有任何共占 Block。
- 相邻边中心 Port 精确配对；类型不同的 Port 无法连接。
- 同一 Module 的 `L→R` 可用，不代表 `R→L` 自动可用。
- 具有多 Port 的 Module，仅连接部分 Port 后，未连接 Port 能被合法封口。
- 使用荆棘封口时，无法从已封口接口意外越界，也不会切断本次需要的 Route。
- 全部 Port 都已连接时，额外存在的 Route 会出现在实际通行图中。
- 水平镜像后端口左右位置变化，起止 Port 身份和权限语义保持正确。
- 初始单向门只在初始可达图中产生允许方向的边。
- 奖励折返、自环、单向环回和异位汇入都能被实际有向图验证。
- 搜索超过预算时仅输出已验证的备用地图，不输出无效候选。

## 12. 推荐系统组件与配置

| 组件 | 阶段 | 推荐职责 |
|---|---|---|
| Module Creator | 离线 | LLM/Codex 辅助制作内容、动作、怪物和机关 |
| Module Validator | 离线 | Godot 路线动作、Port 接缝、封口、镜像认证 |
| Library Compiler | 离线 | 编译 Module 数据、镜像候选、Route 与封口索引 |
| Exploration Planner | 在线、纯程序 | 图变换、主路线目标与奖励支路设计 |
| Spatial Solver | 在线、纯程序 | 矩形 Module 布局、Port 定向连接、闭环与回溯 |
| Map Validator / Ranker | 在线、纯程序 | 静态图可达、真实 Route 完整性、体验排序 |
| Godot Runtime | 游戏运行时 | 实际场景、玩家物理、动态机关与战斗 |


### 12.1 下一阶段最有价值的研究目标

优先完成**指定两个 Port 之间的目标导向连接与环路闭合**，并让同一测试 Module 在不同 Port 子集、不同镜像方向下参与搜索。待这些局部关系可重复、可验证，再扩展到 40～65 个实例与多路线结构。

在此基础上采用“地图需求驱动的 Module 库自增长”：离线优先补缺高频端口签名和玩法组合，使库的**有效连接能力**与**玩家可辨识的动作挑战种类**同步增长。

---

**推荐实现总览：以少量图变换构造有意义的探索目标，以不同尺寸的矩形 Module 和可选 Port 用途提供组合自由度，以简单的局部荆棘/地形封口处理未用接口，以方向候选和 Route 索引减少在线搜索，以目标导向连接、有限回溯及实际有向图验证稳定输出随机大地图。**
