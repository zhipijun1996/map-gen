# 《失序之钟》随机 Map 系统：基础模型与强制契约

> **文档代号：** `MAP_FOUNDATION`  
> **版本：** 1.0  
> **状态：** 规范性文件（Normative）  
> **适用对象：** 《失序之钟》的 Module 制作器、Module 库、Map 生成器、验证器及 Godot 运行时。  
> **规范优先级：** 本文件是 Map 系统的最高优先级设计依据。当算法实现、模块数据、推荐方案、其他设计文档或 Codex 任务描述与本文件冲突时，以本文件为准；如确实需要改变基本模型，应先修订本文件并升级版本。  
> **配套文档：** `MAP_GENERATION_GUIDE.md`（算法、规模、尺寸与实施推荐，不改变本文件定义）。

## 1. 系统目标与边界

《失序之钟》采用在线随机生成的、以平台跳跃与探索为核心的连续大区域 Map。玩家使用跳跃、枪械反作用力位移、钩索、区域机关及其他已解锁能力，在多路线空间中探索、挑战、获取奖励并抵达 Boss。

系统分为两个生产阶段：

- **离线：** 制作 Module、定义 Port 与 Module Route、验证真实动作及接口、编译可供检索的 Module 库。大模型可辅助离线创作，验证结论以程序和实测为依据。
- **在线：** 由纯程序读取已认证的 Module 库和生成输入，组合 Module、构造 Map、验证并实例化。在线流程不调用大模型，也不临时生成新的 Module。

在线 Map 生成接收随机种子、区域配置、已解锁能力集合与 Module 库版本等静态输入。**玩家能力集合仅在生成开始时输入一次；生成过程中不追踪玩家血量、精力、能量、速度、装备变化或机关开启过程。** 运行中这些动态行为由 Godot 游戏系统负责。

本文件使用以下规范词：**必须**代表不可违反的契约；**允许**代表合法的能力范围；**可配置**代表由区域或运行参数确定、但不能突破模型契约的数值。

## 2. 基本对象与空间坐标

### 2.1 Block：唯一地图布局网格

- Block 是 Map 布局的统一整数坐标单位，坐标为 `(x, y) ∈ ℤ²`。
- 默认尺寸为 **128×128 像素**，可配置；所有 Module 的位置及尺寸均以 Block 表示。
- Block 是**布局单位**，不是要求 Cell 的尺寸、形状或视觉表现也按 Block 划分。
- 系统不另设“逻辑槽位”等高一级的强制空间单位。

### 2.2 Cell：Module 内的具体内容

Cell 是岩体、可穿平台、荆棘、齿轮、开关、机关门、怪物、宝箱、奖励、装饰及其他游戏实体的统称。

- Cell 保留自己的像素级形状、碰撞、交互和美术信息。
- 每个 Cell 的**静态布局几何、环境碰撞与边界封口布置**必须受到其所属 Module 的 Block 矩形范围约束。运行时移动的玩家、敌人、弹丸等可以依照游戏规则运动，不将动态移动视为 Module 空间占用重叠。
- Module 边界的跨模块通行由 Port 契约负责。实际游戏画面不需要绘制矩形边框。

### 2.3 Module：矩形 Block 内容单元

一个 Module 是已离线制作、验证并可复用的内容模板，其基本表示为：

\[
M=(W,H,C,P,R,T,Q)
\]

| 字段 | 强制语义 |
|---|---|
| `W, H` | Module 的 Block 宽、高；均为正整数；占据完整的 `W×H` 矩形。 |
| `C` | Cell、地形、敌人、机关与相关实体。 |
| `P` | 位于矩形边界上的 Port 集合。 |
| `R` | Port 到 Port 的有向 Module Route 关系。 |
| `T` | 职责、玩法、能力及难度等静态描述标签。 |
| `Q` | 认证、质量及静态评估资料。 |

Module 可具有穿越、分叉枢纽、奖励、开阔空间等一种或多种职责。职责标签**不限制其实际用法**；实际用法由本次放置时连接的 Port 和真实存在的 Route 决定。

Module 的 Block 占用始终是矩形，尺寸可以因 Module 而异。一个 Map 内的 Module **绝不重叠**；Map 外轮廓不要求为矩形，Module 外缘也不意味着视觉上的房间边框。

### 2.4 Module Instance：一次实际放置

一个实例由如下信息决定：

`Instance = (module_id, origin_x, origin_y, mirror_x, connections, closures)`

- `module_id`：基础 Module 模板 ID。
- `(origin_x, origin_y)`：整数 Block 坐标。
- `mirror_x`：本次是否水平镜像。
- `connections`：此次实例实际与其他实例配对的 Port。
- `closures`：此次实例未连接 Port 的封口配置。

实例矩形覆盖：

\[
[origin_x,origin_x+W)\times[origin_y,origin_y+H)
\]

任意不同实例 A、B 必须满足其覆盖矩形交集为空。**相邻 Module 的 Port 可以共用同一个几何边界点，但其 Block 实体占用不能交叠。**

## 3. Port：Module 之间唯一的合法通行接口

### 3.1 位置与边界朝向

每个 Port 位于指定**边界 Block 的一条外侧边中心**，边界朝向为 `LEFT / RIGHT / TOP / BOTTOM`。

相邻两个 Module 的 Port 连接必须满足：

1. 两个 Port 在世界坐标下位于**同一个边界中心点**。
2. 两个 Port 的外法线**方向相反**。
3. 两者地貌类型兼容；基础模型只允许**同类对同类**。
4. 连接方向与两个 Port 的初始 `INPUT / OUTPUT / INOUT` 权限兼容。
5. 接缝的 Cell、碰撞与动作接口经过离线认证。

可使用双倍整数 Block 坐标保证精确匹配：对于局部 Block `(b_x,b_y)`，左、右、上、下边中心分别是 `(2b_x, 2b_y+1)`、`(2b_x+2, 2b_y+1)`、`(2b_x+1, 2b_y)`、`(2b_x+1, 2b_y+2)`；放置和镜像变换后再比较世界坐标。

### 3.2 Port 的三种地貌类型

| 类型 | 定义与约束 | 允许的边界朝向 |
|---|---|---|
| `AIR` 空中 Port | 接口处没有安全站立地面；进入时按预认证的向下运动情形处理。空中 Input 不可设置于 Module 底边。 | 可位于合法的其他边界；底边不能作为 `AIR INPUT`。 |
| `ROCK` 岩体 Port | 下方必须具有安全的实体岩体支撑。 | 仅 `LEFT`、`RIGHT`。 |
| `ONE_WAY_PLATFORM` 可穿平台 Port | 下方有安全的可穿越平台作为支持。 | `LEFT`、`RIGHT`、`TOP`、`BOTTOM`。 |

三类 Port 只能分别与相同地貌类型的 Port 对接。相邻连接的静态运动接口也应遵循其离线认证前提。由于底边 `AIR INPUT` 被禁止，顶部 `AIR OUTPUT` 在本契约下没有合法的同类相邻 Input，不能作为必须连接的有效向上出口；向上连接可使用经过认证的顶部可穿平台 Port 等合法接口。

### 3.3 初始有向权限

Port 的初始权限为：

- `INPUT`：允许玩家从相邻 Module 经该 Port **进入本 Module**。
- `OUTPUT`：允许玩家从本 Module 经该 Port **离开**。
- `INOUT`：上述两种方向均允许。

一个连接从 Module A 指向 Module B，必须满足 A 侧 Port 具有初始离开权限，且 B 侧 Port 具有初始进入权限。连接可以只有一个有向通行方向，也可以两个方向均成立。

**单向机关 Port** 在在线建图时使用其**初始有向权限**。例如初始关闭的风铃门允许右侧 Module → 左侧 Module，开关位于右侧；在线只建立 `右 → 左` 边。游戏进行中开启后可能成为双向，是运行时机制，不改变初始生成图的定义。只允许到达的一侧并非“物理接口不存在”，而是该方向的出发权限为关闭。

### 3.4 未连接 Port 与封口

**每个 Module 允许仅连接部分 Port；所有未连接 Port 均属于本次实例的未启用接口。**

未连接 Port 必须满足：

1. 在最终场景中不能形成玩家可从 Module 穿出到无效空间的开放通道。
2. 不作为实际 Map 通行图的外部连接边，也不计入所要求的连接数。
3. 使用该 Module 内部已有的封闭地形，或放置**局部封口 Cell**（例如荆棘平台、带碰撞的岩体或荆棘屏障）来处理；封口的实体占用仍位于所属 Module 内。
4. 封口必须实际实现对应边界的不可通行或可控终止，不能仅凭视觉障碍或少量伤害便视为封闭。
5. 所使用的封口配置不得破坏其他实际启用 Port 之间已认证的必要 Route，也不得产生未声明的合法跨模块连接。

空中 `OUTPUT` 若未对接合法的相邻 `INPUT`，则必须作为**无效输出**处理并完成封口，不能保留可穿越的开放边界。岩体与可穿平台 Port 同样遵循上述未启用接口规则。

封口既可以是标准的、可复用的局部荆棘方案，也可以是 Module 自带的天然封闭边界。在线程序仅选择、实例化已认证的封口方案；封口的形态与碰撞效果由离线制作与验证确定。

## 4. Module Route：内部的有向动作关系

假设某 Module 有 `N` 个 Port，其内部通行关系是 `N×N` 有向矩阵：

\[
R[i][j]=\{r_1,r_2,\ldots\}
\]

- 每个矩阵元素包含 **0 条或多条**实际可行的有向 Route。
- `R[i][j]` 与 `R[j][i]` 是独立关系；多 Port Module **不默认所有 Port 两两互通**。
- 允许 `R[i][i]` 自环，例如由同一个 Port 进入、获取奖励、再由同一个 Port 返回；该 Port 仍必须具有与外部连接匹配的初始进入及离开权限（通常是 `INOUT`），自环不自动改变 Port 权限。
- 输入和输出是否能互换，取决于是否分别存在经过认证的对应有向 Route，不因几何相同而自动互换。

每条 Route 至少声明以下契约信息：

| 字段 | 语义 |
|---|---|
| `from_port`, `to_port` | Route 的入口与出口 Port ID。 |
| `displacement` | 入口至出口的局部 Block 位移向量。 |
| `required_abilities` | 完成 Route 所需的能力集合。 |
| `action_tags` | 动作组合与核心玩法，例如反冲射击、二段跳、钩索、战斗。 |
| `difficulty` | 离线统一标尺下的难度描述。 |
| `estimated_duration` | 预计通过时间。 |
| `resource_profile` | 精力、能量、生命等设计需求与消耗/恢复描述。 |
| `initial_conditions` | 该 Route 的初始地貌或机关条件。 |
| `entry_exit_contract` | 离线认证采用的进入、离开与运动接口条件。 |
| `validation` | 真实物理动作验证结果与可追溯记录。 |

所有供在线使用的 Route 必须经过离线认证；在线只对静态必要能力进行过滤：

\[
required\_abilities(r)\subseteq available\_abilities
\]

资源、速度和运行时状态仍可记录在 Route 的**离线契约或评分标签**中，但不作为在线 Map 逐步模拟的玩家状态。

### 4.1 “本次计划使用的 Route”与“实际存在的 Route”

Map Generator 可以为某实例选择要满足的规划路线，但**不能因为没有规划其他 Route，就删除真实存在的 Route**。

例如 Module 有 L、R、U 三个 Port，真实 Route 为 `L→R`、`L→U`、`U→R`：

- 只连接 L、R：此次可以承担普通穿越，U 按未连接 Port 规则封口。
- 连接 L、U：此次可以承担向上穿越，R 封口。
- 连接 L、R、U：此次可能成为分叉或汇合；全部在初始条件下可行的 Route 都必须计入实际通行图。

当 Route 通向未连接 Port 时，该 Port **没有外部通行边**；相应局部封口不能破坏本次需要使用的 Route。若封口导致某条 Route 不再可完成，该封口组合仅能在已认证允许这种失效的前提下选用，并且最终实际 Route 图必须反映其真实可行性。

## 5. 水平镜像与模板身份

- 每个基础 Module 可以声明是否支持 `mirror_x`；运行时只使用经过认证的方向。
- **一个基础 Module 仍然是一个模板**；原向与水平镜像是至多两个放置方向变体，而非两个独立制作的 Module。
- 镜像必须同时作用于所有 Cell、Port、地形碰撞、机关、视觉与左右方向相关的行为。
- 对宽度为 `W` 个 Block 的 Module，局部 Block 横坐标变换为 `x' = W−1−x`；若 Port 使用双倍边界坐标，则 `u' = 2W−u`。
- `LEFT ↔ RIGHT`；`TOP`、`BOTTOM` 不变。`INPUT / OUTPUT / INOUT` 的**通行语义不互换**。
- Route 的起止 Port ID 可以保持不变，随 Port 的镜像位置映射到新的几何方位；水平位移、方向性动作参数相应取反。
- **镜像不是将 `N×N` Route 矩阵转置。**

统计基础库规模时，镜像方向不增加基础 Module 数量；统计搜索候选数时，可将合规方向变体独立索引。完全对称且玩法等价的方向可合并。

## 6. Map：已放置 Module 的真实探索网络

Map 同时包含：

1. **二维布局：** 全部 Instance 的整数 Block 坐标及矩形占用。
2. **实际 Port 连接：** 已启用且满足几何、地貌与初始方向规则的跨实例接口。
3. **实际有向通行图：** 通过 Module 内可用 Route 和跨 Module Port 连接构造的有向图。
4. **探索内容：** 起点、Boss、奖励、机关、地标及其静态配置。

**实际通行图的节点必须至少能区分实例与 Port**；跨同一 Module 的通行只能通过该实例真实可行的 Module Route 实现，不能仅凭同属一个 Module 推定可达。

应当区分：

- **规划探索图：** 生成器希望实现的主路线、分叉、汇合、捷径和奖励关系。
- **实际有向通行图：** 玩家在地图初始条件下、使用生成输入所含能力，依据全部真正接通且有效的 Route 能够采取的通行关系。

最终验证以**实际有向通行图**为准。未计划但实际可行的绕行与捷径同样属于真实地图结构。

## 7. 初始状态、能力与运行时边界

在线生成的静态能力输入为：

`available_abilities = {能力 ID ...}`

生成期间：

- 可以依据能力集合过滤 Route。
- 可以依据 Route 的难度、时长、玩法和资源描述进行静态规划、评分和统计。
- 可以依据机关门的**初始通行方向**构造有向边。
- **不**追踪每一步玩家速度、精力、能量、血量、背包变化，也**不**模拟逐步开关机关。

Godot 运行时负责后续物理运动、机关开启、奖励拾取与玩家状态变化。初始图中必需完成的路线，不能依赖未纳入初始有向图的开门后连接。如果某个特殊谜题必须通过运行时开门才能返回，则应以经过离线认证的完整特殊结构实现，并在其相关玩法契约中明确，而不能让通用在线静态验证把未打开的门当成已打开。

## 8. 必须遵循的完整性和验证条件

Map Generator 输出的每张正式地图，都必须满足以下条件：

1. **整数矩形占用：** 所有 Instance 为整数 Block 坐标的 `W×H` 矩形；任意两个矩形不重叠。
2. **接口合法：** 每个连接的 Port 坐标重合、外法线相反、同地貌类型、初始通行权限兼容。
3. **封口完整：** 所有未连接 Port 采用已认证边界或封口配置；无可意外越界的开放出口。
4. **真实 Route：** 每条被用于通行的内部 Route 都存在、满足必要能力、具有有效离线认证，并与本次封口配置兼容。
5. **完整有向图：** 实际有向图包含所有真正成立的已连接 Port 与 Route，不仅包含生成器最初计划的路线。
6. **基础可达：** 在初始有向图中，玩家从 Start 至 Boss 至少有一条合法通路；区域配置规定为必需的目标也必须可达。
7. **奖励去向：** 奖励支路具备所声明的折返、单向环回或异位汇入关系；对需要返回主网络的奖励，存在经初始图证明的合法去向，或采用已认证的特殊完整玩法结构。
8. **内容契约：** Module、Port、Route、镜像和封口均来自与目标运行版本兼容的离线认证资料。
9. **生成边界：** 正式在线生成采用纯程序、有界的计算预算；只有通过上述条件的候选 Map 才能进入实际游戏。

在线验证的结论是**初始状态下、静态能力约束和已认证 Route 接口上的拓扑可达**；并不宣称可证明任意玩家资源状态下必然通关。真实动作手感与物理可靠性通过离线 Godot 测试、运行时测试及试玩保证。

## 9. 文档治理与兼容原则

本文件固定核心数据模型与强制契约，不固定某一种搜索算法、具体 Module 库数量、推荐尺寸分布、探索图生成规则、评分权重或性能目标。这些在 `MAP_GENERATION_GUIDE.md` 及区域配置中规定和迭代。

解释顺序：

1. **本文件 `MAP_FOUNDATION.md`**：最高优先级，基本定义与必须满足的契约。
2. **区域及 Module 的已认证数据和显式配置**：在本文件允许的范围内提供具体内容和数值。
3. **`MAP_GENERATION_GUIDE.md`**：默认算法、库规模、尺寸、性能和实施建议。
4. **具体实现任务、Codex Prompt 与开发实验**：遵守以上契约。

若需调整本文件的强制规则，应通过一次完整版本修订统一更新数据、验证器与配套文档；不通过在其他文档中添加例外来覆盖。

---

**基础架构定义：以 Block 为唯一布局网格，以不重叠的矩形 Module 为内容单位，以可部分启用并合法封口的 Port 为跨模块接口，以多条有向 Module Route 为内部真实动作关系，以水平镜像提高复用，以固定能力和机关初始方向构造在线有向图，并由纯程序完成在线生成与验证。**
