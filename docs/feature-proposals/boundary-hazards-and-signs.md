# 后续功能：边界移动齿轮与分岔告示牌

状态：设计记录，尚未实现；来自本轮新增用户需求。0.8.0的算法、冻结输入/结果和交付包不混入这些功能，不自动升级模块包或改主游戏。后续实际实现需独立版本、同seed开关对照及三仓接入验证。

## 一、边界移动齿轮

用户目标是增加绕过Port的跨界成本，保持画面稀疏、美观；不是沿每个矩形边铺满，也不是用随机齿轮替代可靠边界证明。移动齿轮留下时间窗口，不能保证完全封死非法穿越。若最终需要严格禁止，须另外设计碰撞/边界规则，不能靠提高齿轮数量掩盖。

生成顺序：

1. 完成模块拼接、合法连接、封口和完整可达检查，形成稳定布局。
2. 将共享边界去重成区段，区分Port通道、已有封口、其他内部接缝和外轮廓。依据真实碰撞几何筛出可能绕过Port的跨界区段；模块AABB边界本身不等于可通行或非法路径证明。
3. 扣除保护区：连接Port及接缝净空、声明作者路径及玩家体型扩张带、普通与目标奖励领取区、重要交互区。出生/Boss等锚点若尚无精确安全区，不在附近盲放。
4. 优先覆盖少量有证据的高风险区段，再对其余合格边界低概率抽样；按整图组数、最小间距、局部密度和扫掠覆盖比例限制，避免全屏均匀铺线。32规模地图可先实验6–10组、同一局部范围1–2组，数字是待验证建议，不是已提交默认参数。
5. 检查完整运动包络，而非只检查初始点。齿轮半径加玩家净空后的扫掠范围不得侵入保护区，不得阻断领奖、必需机关或合法接缝。优先沿边界往返，运动端点、速度/周期、相位由独立确定性随机流产生。

优先处理高风险内部接缝，外轮廓挑关键点；其余区段随机保留大片空白。局部密度预算应同时计入已有模块saws/hazards和静态Port齿轮封口，已有危险密集的地方不继续加码；不重复生成，也不修改源模块。新增项属于地图级附加危险，map-gen输出纯数据和稳定身份，主游戏复用/实现移动齿轮组件并处理碰撞、伤害、调度和卸载；map-edit提供局部允许/禁止区域等作者约束。

若只有静态几何候选，结论必须是“候选越界区段”，不能宣称真实动作漏洞已定位。没有安全候选时少放/不放，并记录原因；不能为凑数侵入保护区。需实际玩家跨界、跳跃、反冲、平台变化及领奖测试验证难度，而不是只看静态图。

## 二、每个实际分岔的可交互告示牌

以实际决策点为单位，而非“某模块有三个Port就放一块”。多个Port可能单向、互不连通或只是在同一通道进出；模块内部也可能有多个物理岔口。每个应标决策点都要有告示牌或明确可审查的锚点缺口，不能静默漏牌后报告完成。

建议首版交互：靠近按键“查看路线”，显示方向箭头和简洁标签：

- “奖励 · 需折返”；
- “奖励 → 汇合主路”；
- “Boss方向”或“直接前往Boss”；
- 多条主路线可分别标注，不把所有能最终到Boss的方向都混成同一个提示。

标签基于该方向在下一决策点/重汇合前的路线段及已证明的奖励支路用途。重汇合以后共享的Boss/奖励不重复归给每个入口，否则所有方向都会显示同一串内容。需处理有向环与单向权限，不假设同模块所有Port互通。主路线推荐应有生成时指定的路线身份，不能把“最短路”自动等同主路。

奖励既包括六个目标奖励，也包括模块内已导出的普通reward_sites；输出稳定实例/站点引用。生成器提供方向绑定、目的类型、关联奖励/Boss及汇合关系；主游戏负责交互UI、本地化、已领取/已击败显示与玩家接近状态。钱包、玩家节点和任务运行token不进入生成算法或确定性指纹。已领取状态由宿主更新显示，不重生成布局。

告示牌位置需有可站立/可交互安全锚点，避免挡路、平台边缘、封口、机关和伤害区。位置与方向绑定随模块镜像/平移正确变换；路线Port方向不因镜像倒转。

## 三、现有1.1.0输入核对及最小补充

已递归核对115个模块catalog和compiled JSON：有ports、reward_sites、platforms、hazards/saws等内容，但未找到通用decision/signage/socket/interaction_anchor及hazard_zone/hazard_band/safe_zone元数据。证据见validation/joint-route-construction-20261105/new-feature-input-inventory.json。该核对不等于作者工具没有这些能力，只表示当前锁定输出没有相应通用语义。

告示牌需要map-edit最少提供：**安全牌位、稳定决策点身份、各方向到真实Port或Route的绑定**。若已有等价交互锚点，优先复用；不要另造一套奖励内容字段。仅靠Port端点和路线折线，map-gen无法保证自动挑到玩家能站住并交互的内部岔口。

齿轮可以先从边界和碰撞几何推候选，若需要可靠的作者控制，则最少补充“允许运动的边界区段/禁止进入区域”。具体Schema、版本及镜像变换由实际三仓实现时收口；此设计不向runtime-map/v2塞入尚无宿主支持的字段，也不假装1.1.0已经有这些锚点。

## 四、确定性与验收边界

两个功能都作为布局之后的可选、独立版本阶段。随机流由seed、稳定布局身份、功能版本和配置派生；开关齿轮或告示牌不改变基础布局、作者图、奖励位置或核心搜索RNG。完整交付内容和恢复身份仍需包含新增阶段版本/配置/内容摘要，不能沿用旧map_id冒充相同产物。

地图级附加数据的公共协议由map-gen维护，主游戏装配内部类型不成为依赖。复用已有扩展能力；若没有，实际实施时再确定兼容的最小交付合同，不预造大量未使用字段。

验收至少包含：同seed开关基础布局不变；运动包络与保护区无冲突；数量/间距/局部密度/画面效果；分岔告示牌覆盖及方向正确；折返/归并/普通奖励/Boss提示；已领取状态变化；镜像与单向Route；可取消调度；真实桌面/Web伤害与交互。本轮均未实现，不能计入0.8.0验证通过。
